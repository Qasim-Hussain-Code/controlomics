# Project format 0.1.0

The initial format is one UTF-8 JSON document. The `manifest.format` is `controlomics.project`; schema and ontology versions are `0.1.0`. Package version is recorded separately and may include a development suffix. Unsupported schema or ontology versions are rejected. There is no migration implementation yet.

Required top-level records are `manifest`, `analysis`, `claims`, and `privacy`. Optional arrays are `claim_relations`, `evidence`, `candidates`, `controls`, `execution_plans`, `results`, `audits`, and `provenance`. Empty arrays mean no records were supplied, not that a review found no problems. Unknown keys are rejected. Required scientific text must contain a nonwhitespace character. JSON timestamps must include a timezone.

All project, analysis, claim, evidence, control, execution, result, audit, and provenance IDs must be globally unique. References must resolve locally. A reviewed control replaces the corresponding candidate record in a project snapshot rather than duplicating its control ID in both arrays. Preserve the candidate snapshot separately when needed. Claim relations may describe scientific dependencies, but there is no causal inference algorithm or graph-cycle interpretation.

Evidence identifiers are typed by namespace and issuing authority. DOI comparison is case-insensitive. Identical DOI, PMID, PMCID, or authority-scoped accession keys across records require consolidation. Disjoint aliases cannot be recognized from syntax alone; retrieval imports consolidate records when official metadata supplies connecting identifiers. Identity checks are distinct from statement-specific evidence links. A review receipt is an attestation, not authenticated proof.

Checked identities must follow retrieval, entailment checks must follow recorded identity checks, and control review must follow its entailment checks. EVIDENCE_BACKED requires human-kind supporting receipts for the exact rationale and expected behavior, an allowed context assessment, and no recorded contradiction. Automated statement receipts cannot satisfy this requirement. METHOD_BASED is restricted to technical and statistical specifications. Reviewed-control records accept only reviewed states; a review receipt cannot coexist with an unreviewed candidate state. These checks apply to imported projects, without authenticating supplied receipts. Control input IDs must be unique. Privacy classification cannot understate declared input or control requirements. Timestamp and classification consistency do not establish the underlying scientific facts.

Execution inputs must match the control specification. Completed results must record hashes for all and only the specified inputs. Result seed and control ID must match the execution plan. PASS or FAIL requires a matching decision rule specified before execution began. Recorded software versions describe the actual execution and may differ from planned versions; scientific review must assess such deviations. ROBUST assessments cannot reference nonpassing results, and CONTROL_FAILURE requires a failed scientific outcome, distinct from software execution failure.

Provenance refers to existing record IDs and records no raw research data by default. Raw query and prompt storage is excluded from the initial provenance model; query and template hashes can be recorded. Users must still review free-text fields for private content. A project can contain confidential scientific descriptions even when it is structurally valid.

The local loader limits input to 2 MiB and rejects duplicate JSON keys, nonfinite JSON constants, malformed records, and unresolved references. The CLI emits redacted failures. Direct use of Pydantic's JSON parser bypasses the duplicate-key and file-size checks, so untrusted projects should enter through `parse_project_json` or `load_project`.

The checked-in `schemas/0.1.0/*.schema.json` files describe structure using JSON Schema draft 2020-12. Python post-validation additionally checks evidence gates, context summaries, ID uniqueness, relationships, and timing. Third-party JSON Schema acceptance alone does not establish these invariants. The ontology is a separate versioned vocabulary file under `ontology/`.

The package version advances independently while the project and ontology formats remain 0.1.0. Intake, hosted proposals, candidate specifications, additional claims, human reviews, reasoning drafts, execution configurations, and evaluation inputs are separately typed workflow records. Nineteen auxiliary schema exports are in `schemas/workflow/0.1.0`. The ten core schemas cover the original nine records and project container. Network events are a separately exported sidecar rather than part of the project schema. Project privacy flags still prohibit transmission of the project; separately selected public fields require their own exact-request approval.

Revised unreviewed candidates retain their ID and a superseded snapshot hash. Reviewed specifications cannot be changed through candidate editing. A `HumanReview` replacing a prior review must supply `supersedes_review_sha256` matching the current reviewed record. The previous hash enters provenance; retain old exports to recover their content. Repeat retrieval preserves the earlier verified identity prerequisite of existing reviews. Neither timestamp continuity nor hashes authenticate a receipt.

Evaluation datasets and bundles use independent `controlomics.evaluation_dataset.v0.1` and `controlomics.evaluation.v0.1` formats. They do not populate project evidence or promote control states. See [EVALUATION.md](EVALUATION.md).

Execution packages use `controlomics.execution.v0.1` manifests with configuration, a plan, control, result schema, environment, fixed scripts, and artifact hashes. The saved project snapshot records one plan per control for that run. Results bind to the control, plan, input hashes, seed, prespecified rule, and runner hash. These bindings do not prove that execution occurred. Retain separate snapshots for reruns. Human review retains source hashes and locators, not full supplied source text.

Future changes to the project format require an explicit migration policy and security review.
